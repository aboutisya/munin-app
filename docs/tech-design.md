## 1. Архитектура

### Стек

- Swift 6, SwiftUI и AppKit там, где SwiftUI не справляется (`NSStatusItem`, окно названия поверх всех окон, глобальный хоткей).
- **Минимальная версия: macOS 15.0.** Нужны process taps, Observation, новое API EventKit. Поддержка старых версий не требуется: машина одна.
- Хранилище: файлы на диске — источник истины. SQLite с FTS5 (GRDB) — только индекс для поиска, его можно пересобрать из папок.
- Внешние процессы: `mlx_whisper` (Python, MLX), `claude` CLI, `ffmpeg`.
- Сборка одной командой: `make app` (SwiftPM → сборка `.app` → подпись) или `xcodebuild`, если поставим Xcode.

## 2. Захват звука

### Сравнение API для системного звука

| Критерий | **Core Audio process taps** | ScreenCaptureKit |
|---|---|---|
| Версия macOS | 14.2+ | 13+ (звук), 15+ (микрофон в том же потоке) |
| Разрешение | «Только запись системного звука» (`NSAudioCaptureUsageDescription`) | «Запись экрана» целиком. Пугает, а в macOS 15 система периодически переспрашивает |
| Индикатор | Значок записи звука | Фиолетовый индикатор записи экрана |
| Выбор источника | Все процессы, кроме своего, или список процессов (Zoom, браузеры, Mattermost) | По приложениям и окнам; звук привязан к захвату контента |
| Зависимость от устройства вывода | Нет: tap снимает звук процесса до устройства, поэтому AirPods, динамики и проводные наушники дают одинаковый сигнал | Тоже нет |
| Сложность | Низкоуровневый C API (`CATapDescription`, aggregate device), документации мало | Высокоуровневый API, больше примеров |
| Задержка и формат | Буферы IOProc, float32, частота устройства | `CMSampleBuffer`, 48 кГц |

**Решение: Core Audio process taps.** Узкое разрешение без записи экрана и без индикатора экрана, сигнал не зависит от устройства вывода. ScreenCaptureKit не берём: он требует разрешение на запись экрана, а нам нужен только звук.

Режим tap по умолчанию: **все процессы, кроме «Мнемозины»**. Так ловится и Zoom, и Meet во вкладке браузера, и звонок Mattermost (Electron). Минус: в запись попадут уведомления и музыка. Решено оставить этот режим единственным в v1, без настройки списка процессов.

### Микрофон

- `AVAudioEngine`, отдельная дорожка. Устройство ввода выбираем через `kAudioOutputUnitProperty_CurrentDevice`, системный микрофон по умолчанию не трогаем.
- Обе дорожки помечаются host time первого буфера. Смещение между ними пишется в `meta.json` и учитывается при склейке.
- Во время записи пишем в CAF (переживает падение приложения), после Stop конвертируем в AAC m4a. После падения при следующем запуске приложение предлагает восстановить запись.

### Устройства вывода и выбор микрофона

`DeviceMonitor` определяет тип текущего устройства вывода по `kAudioDevicePropertyTransportType` и data source (у встроенного выхода это «Внутренние динамики» или «Наушники» для джека).

| Вывод | Микрофон по умолчанию | Эхо | Что делаем |
|---|---|---|---|
| AirPods / BT-наушники | **Встроенный микрофон MacBook** | Нет | Обычная запись. Микрофон AirPods не берём: при его включении macOS переводит гарнитуру в профиль HFP, и звук в ушах становится 16 кГц моно |
| Проводные наушники | Встроенный (или микрофон гарнитуры, если выбран) | Нет | Обычная запись |
| Встроенные динамики / внешние колонки / HDMI | Встроенный | **Да** | Эхоподавление в три слоя (ниже) |
| Крышка закрыта, встроенного микрофона нет | Выбранный в настройках, затем системный по умолчанию | Зависит от вывода | Предупреждение в поповере |

Важная деталь для AirPods: если **сам Zoom** берёт микрофон AirPods, профиль HFP всё равно включится, что бы ни делал «Мнемозина». В онбординге подсказываем выставить в Zoom и Meet микрофон MacBook. В настройках можно выбрать любой микрофон, а для BT-микрофона показываем предупреждение о качестве.

Смена устройства посреди записи (например, достали AirPods из кейса): tap не прерывается, микрофон переподключается, событие пишется в `meta.json`. Если вывод переключился на динамики, включается эхоподавление.

### Эхоподавление при динамиках

1. **Voice processing на микрофоне.** `inputNode.setVoiceProcessingEnabled(true)`: встроенный AEC Apple использует системный вывод как опорный сигнал. Приглушение чужого звука выставляем минимальным (`voiceProcessingOtherAudioDuckingConfiguration`), иначе звонок станет тише. Включаем **только в режиме динамиков**: в наушниках voice processing лишь портит тембр.
2. **Энергетический гейт.** После записи оцениваем задержку между дорожками (GCC-PHAT по первым минутам), затем для каждого окна 50 мс сравниваем: если сигнал в микрофоне объясняется сигналом системной дорожки, а собственная энергия микрофона ниже порога, окно помечается как эхо. Остаточное эхо после AEC обычно тихое и коррелирует с системной дорожкой.
3. **Дедупликация на уровне транскрипта.** Сегмент «Я», который пересекается по времени (±1,5 с с учётом задержки) с сегментом собеседника и похож на него по тексту (нормализованное расстояние Левенштейна по словам, порог около 0,6), удаляется, если в этот момент на системной дорожке была речь. Порог подбираем на тестовых записях. Этот слой покрываем юнит-тестами.

Критерий проверки из MVP («нет дублей чужих реплик на моей дорожке») проверяем записью тестового звонка через динамики с контрольной фразой собеседника.

### Режимы записи

| Режим | Дорожки | Спикеры |
|---|---|---|
| **Онлайн** | Системный звук + микрофон | «Я» — микрофон целиком; собеседники — диаризация системной дорожки |
| **Офлайн** | Только микрофон | Диаризация микрофона; «Я» определяется по голосовому отпечатку |
| **Гибрид** | Системный звук + микрофон | Диаризация обеих дорожек; на микрофоне «Я» по отпечатку, остальные — «В комнате N» |

Автоопределение при старте:
- у события есть ссылка на звонок (Контур.Толк `*.ktalk.ru`, meet.google.com, zoom.us, SberJazz `jazz.sber.ru`, МТС Линк `*.mts-link.ru`, ссылка Mattermost) или звонок в Telegram или процесс звонка выдаёт звук → онлайн;
- у события указана переговорная и нет ссылки, а системного звука нет первые 60 секунд → офлайн (предлагаем переключиться, не переключаем молча);
- гибрид автоматически не угадываем, только вручную или по признаку «у события есть и переговорная, и ссылка».

**Голосовой отпечаток (входит в v1).** В онбординге просим прочитать абзац (15–20 секунд), сохраняем эмбеддинг голоса в `~/Meetings/.people/`. Он нужен в офлайн- и гибрид-режиме, чтобы отличить меня от людей в комнате. Перезаписать можно в настройках «Люди и голоса».

### Таймер и напоминание

Иконка в строке меню (`NSStatusItem`) в двух состояниях:
- **ожидание** — шаблонная иконка «волна голоса» 18×18 pt (`isTemplate = true`), macOS сама красит её под светлую и тёмную строку меню;
- **запись** — та же шаблонная «волна» с маленькой красной точкой в углу. Без таймера и цветного фона, чтобы не отвлекать на встрече; таймер виден в поповере.

Через N минут после конца привязанного события (по умолчанию 10) приходит уведомление «Похоже, встреча закончилась» с кнопками «Остановить» и «Ещё 15 минут».

## 3. Календарь

- EventKit, `requestFullAccessToEvents`. Подхватывает аккаунты Google и Exchange, добавленные в Календарь macOS.
- Берём название, время, организатора, приглашённых (имя, email, статус), описание или повестку, место, ссылку на звонок.
- **Выбор события при записи:** события, которые идут сейчас (±5 минут от начала), без событий на весь день и без отклонённых. Приоритет у событий со ссылкой на звонок и с другими участниками. Если подходящих несколько, показываем выбор. Алгоритм покрываем тестами.
- Уведомление за минуту до начала: «Начинается «Синк по релизу» — записать?» с кнопкой «Записать».
- Событие меняется в поповере и в карточке встречи, есть вариант «Без события».
- **Перепривязка из карточки.** Кнопка «Перепривязать» рядом с событием открывает список событий, которые пересекаются со временем записи, поиск по другим событиям и вариант «Без события». После выбора обновляются `meta.json` (событие, организатор, повестка) и, если стоит флажок, список участников. Название встречи не трогаем, если вы его уже меняли. Повторный анализ не запускается автоматически: в карточке появляется подсказка «Участники изменились — обновить саммари?», это один вызов Claude.

## 4. Транскрибация и диаризация

### Транскрибатор

Нашёлся **mlx-whisper + whisper-large-v3-turbo**: на Apple Silicon это быстрый вариант с хорошим русским.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **mlx-whisper (есть)** | Уже стоит, модель скачана, быстрый на MLX, выдаёт JSON с таймкодами слов | Python-процесс снаружи; окружение `uvx` лежит в кэше и может быть удалено при чистке |
| WhisperKit (Swift, CoreML) | Работает внутри приложения, без Python | Модель придётся качать заново, на большой модели медленнее MLX (допущение, проверим) |
| whisper.cpp | Без Python, Metal | Не установлен, модель в другом формате |

**Решение для v1: mlx-whisper**, переведённый в постоянную установку `uv tool install mlx-whisper`. Вызов из приложения: `mlx_whisper <wav> --model mlx-community/whisper-large-v3-turbo --word-timestamps True --output-format json`. Транскрибатор спрятан за протоколом `Transcriber`, поэтому позже можно перейти на WhisperKit без переделки конвейера.

Детали:
- **Язык:** по умолчанию `ru`. Если в настройках выбран «Авто», язык определяем по первым 30 секундам каждой дорожки. Английские вставки large-v3 обычно пишет латиницей и в режиме `ru`.
- **Подсказка (initial prompt):** имена приглашённых и словарь терминов из настроек. Так лучше распознаются имена и названия продуктов.
- **Галлюцинации на тишине.** Whisper на паузах выдаёт «Продолжение следует…», «Субтитры сделал…» и похожие фразы. Перед распознаванием вырезаем тишину через VAD, после распознавания фильтруем по стоп-списку.
- Скорость: часовая дорожка на M4 Pro, по нашей оценке, распознаётся за 3–6 минут (допущение, замерим на этапе 3). Две дорожки обрабатываются последовательно, чтобы не делить GPU.

### Диаризация

Сейчас её нет. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **FluidAudio** (Swift, CoreML, модели на базе pyannote и WeSpeaker) | Работает внутри приложения, на Neural Engine, без токена Hugging Face, отдаёт эмбеддинги спикеров | Молодая библиотека, качество на русском нужно проверить |
| pyannote.audio (Python) | Эталон по качеству | Нужен токен Hugging Face для закрытой модели, torch на MPS, медленнее |
| sherpa-onnx | Кроссплатформенный, без токена | Качество ниже, больше ручной сборки |

**Решение: FluidAudio**, за протоколом `Diarizer`. Если на тестовых записях качество окажется слабым, переключаемся на pyannote через `uv`. Сравнение делаем на этапе 3 на двух-трёх реальных записях.

### Склейка

1. Слова whisper получают спикера по максимальному пересечению с отрезками диаризации.
2. Дорожка «Я» целиком помечается как «Я» (в онлайн-режиме).
3. Соседние сегменты одного спикера склеиваются в реплики.
4. Дедупликация эха (§2).
5. Результат: `transcript.json` (машинный: слова, таймкоды, спикеры, дорожка) и `transcript.md` (для чтения: `**[00:12:34] Мария:** текст`).

### Сопоставление спикеров с людьми

- Источники: приглашённые из календаря, голосовые отпечатки людей из прошлых встреч, имена, прозвучавшие в разговоре (их предлагает Claude в вызове 1).
- В UI спикера можно переназначить: «Собеседник 2 → Мария Смирнова». Правка сохраняет эмбеддинг голоса в `~/Meetings/.people/people.json`. На следующих встречах человек подставляется автоматически, если голос похож (косинусная близость выше порога) **и** человек есть среди приглашённых. Без приглашения приложение только предлагает вариант с пометкой «?».
- После переназначения транскрипт и саммари обновляются **заменой имён**, без повторного вызова Claude.
- **Ручное добавление участника.** Кнопка «Добавить» в блоке «Участники»: выбор из приглашённых в событии или новый человек (имя, необязательный логин Mattermost). Если человек не говорил, он отмечается как присутствовавший без реплик. Добавление сохраняется в `meta.json` и в `people.json`.

## 5. AI-анализ через Claude Code CLI

### 5.1. Как вызываем

```bash
# окружение процесса: копия env без ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN,
# ANTHROPIC_BASE_URL, CLAUDE_CODE_USE_BEDROCK, CLAUDE_CODE_USE_VERTEX
cd ~/Meetings/2026-11-24_1430_Синк/
claude -p "/meeting-analysis" \
  --model sonnet \
  --output-format json \
  --json-schema "$(cat analysis.schema.json)" \
  --tools "" \
  --strict-mcp-config \
  --no-session-persistence \
  --setting-sources user \
  < analysis_input.md
```

- Транскрипт и метаданные передаём через stdin одним блоком: так вызов укладывается в один ход модели и не тратит лимиты на чтение файлов.
- `--tools ""` и `--strict-mcp-config`: модели не нужны инструменты и MCP-серверы, они только раздувают системный промпт.
- `--json-schema`: CLI проверяет структуру ответа, приложение получает готовый объект в `structured_output`.
- **`--bare` не используем**: он отключает авторизацию по подписке.
- Модель берётся из настроек: Sonnet по умолчанию, Opus по желанию. Предупреждаем, что Opus расходует лимиты быстрее.

### 5.2. Проверка подписки (онбординг и перед каждой очередью)

1. `claude --version`: CLI установлен.
2. `claude auth status`: `loggedIn: true`, `authMethod: claude.ai`, `subscriptionType: max`.
3. В `~/.claude/settings.json` нет `apiKeyHelper` и `env.ANTHROPIC_API_KEY`: они тоже переключают CLI на платный API.
4. В окружении самого приложения нет `ANTHROPIC_API_KEY` (если есть, показываем предупреждение, хотя при вызове переменная всё равно удаляется).
5. Срок логина (`loginExpiresAt`): за 3 дня до истечения напоминаем перелогиниться через `claude /login`.

### 5.3. Сколько вызовов на встречу

**Два вызова:**

| Вызов | Скилл | Вход | Выход |
|---|---|---|---|
| 1. Анализ | `meeting-analysis` | Транскрипт, событие календаря, известные люди, режим | `analysis.json`: всё для личного саммари |
| 2. Публичное | `meeting-public`, затем `/ru-text` | **Только публичное подмножество** `analysis.json`: TL;DR, договорённости, action items, список диаграмм | `summary_public.md` |

Во второй вызов приложение передаёт только разрешённые поля. Тональность, оценки участников и фидбек по речи туда физически не попадают, поэтому не могут утечь в публичный текст.

Повторно ничего не обрабатываем: каждый шаг записывает в `meta.json` хэш входа (транскрипт + версия скилла + модель). Если хэш не изменился, шаг пропускается. Переименование встречи и переназначение спикеров не требуют новых вызовов.

Встречи длиннее 2,5 часов делим на части по темам: каждая часть анализируется отдельно, затем делаем короткий вызов для сводки. Это единственный случай, когда вызовов больше двух.

### 5.4. Оценка расхода на часовую встречу

| | Вызов 1 (Sonnet) | Вызов 2 (Sonnet) |
|---|---|---|
| Системный промпт CLI | ~7 тыс. токенов (замер) | ~7 тыс. |
| Скилл | ~6 тыс. (SKILL.md + справочник по переговорам) | ~4 тыс. + `/ru-text`: SKILL.md и 2 справочника, ~10–12 тыс. |
| Данные | Транскрипт ~25–35 тыс. (допущение: ~8 тыс. слов за час) | ~2–3 тыс. |
| Выход | ~8–12 тыс. | ~2–3 тыс. |
| **Итого** | **~50 тыс. на вход, ~10 тыс. на выход** | **~35 тыс. на вход, ~3 тыс. на выход** |

Anthropic не публикует лимиты Max 5x в токенах, поэтому точную долю лимита посчитать нельзя. По ощущению это сравнимо с двумя-тремя средними задачами в Claude Code. Приложение записывает `usage` каждого вызова в `meta.json` и показывает в настройках расход за день и неделю, так что через пару недель у нас будет реальная цифра.

**`/ru-text` вызывается как есть.** Скилл сам решает, какие справочники читать, и для делового сообщения берёт два небольших файла. Для этого во втором вызове разрешены инструменты `Skill` и `Read` только для папки `~/.claude/skills/ru-text/` (`--allowedTools "Skill" "Read(~/.claude/skills/ru-text/**)"`). Так вы правите `ru-text` у себя, а приложение сразу пользуется новой версией. Humanizer не подключаем.

### 5.5. Лимит исчерпан

- Распознаём по ответу CLI: `is_error: true` и `api_error_status: 429` или текст вида «usage limit reached… resets …».
- Задача получает статус **«В очереди: лимит подписки, повтор в 15:10»**. Время берём из ответа, если оно там есть, иначе повторяем через 15 → 30 → 60 минут.
- Очередь хранится на диске (`~/Meetings/.queue.json`) и переживает перезапуск и сон Mac.
- Пока ждём, транскрипт уже доступен в карточке, а саммари показываются как «ожидают анализа».
- Кнопка «Повторить сейчас» в карточке и в поповере.

### Структура

```

│       └── diagrams.md          — когда строить диаграмму, допустимые типы Mermaid

│   ├── SKILL.md                 — формат Mattermost Markdown, что запрещено
│   └── references/
│       └── mattermost-format.md — что поддерживает Mattermost Markdown
```

Справочник по переговорам скилл встраивает в свой текст при вызове (через `@references/…` в SKILL.md), а не читает инструментом: у вызова нет инструментов. Схема выхода `analysis.schema.json` лежит в бандле приложения: приложение передаёт её флагом `--json-schema` и само проверяет версию. Версия скилла указывается в frontmatter (`metadata.version`) и входит в хэш шага.

Вы правите скиллы без пересборки приложения. Если после правки поле пропало или изменило тип, приложение показывает ошибку разбора с текстом ответа и не теряет транскрипт.

### Вызов 2: публичное саммари

Скилл `meeting-public` формирует текст в Mattermost Markdown (заголовки `####`, списки, жирный, таблица для action items, без Mermaid и HTML), затем вызывает `/ru-text` для вычитки и возвращает только итоговый текст. Ответственные пишутся именами, без `@`-упоминаний. Диаграммы вставляются как ссылки на PNG: в Mattermost их нужно прикладывать картинкой.

## 7. Диаграммы

- `mermaid.min.js` лежит в ресурсах приложения (без CDN), рендер в `WKWebView` с темой под светлую и тёмную тему системы.
- Экспорт в PNG через `WKWebView.takeSnapshot` с масштабом 2x, файлы в `diagrams/`.
- Если Mermaid не парсится, показываем исходник и ошибку, а в публичное саммари диаграмма не попадает.

## 8. Публичное саммари и Mattermost

- Редактор с предпросмотром. Правки сохраняются в `summary_public.md`, исходный ответ модели остаётся в `summary_public.generated.md`.
- «Скопировать текст» и «Скопировать диаграмму» — отдельные кнопки: Mattermost при вставке не принимает текст и картинку одним блоком.
- Кнопка **«Копировать публичное»** стоит в шапке карточки и работает с любой вкладки, а также по хоткею ⌘⇧C. В буфер попадает текущая версия `summary_public.md` с вашими правками, в виде plain text Markdown. После копирования кнопка на 2 секунды становится зелёной: «Скопировано».
- Позже: отправка через incoming webhook в выбранный канал, всегда с окном подтверждения и предпросмотром.

- Аудио, транскрипты, индекс, голосовые отпечатки хранятся только на Mac.

- На встрече можно поставить флажок «Не анализировать»: приложение сделает только транскрипт.
- Приложение не отправляет телеметрию.
- Запись собеседников: в онбординге короткая памятка предупреждать участников о записи.

## 11. Ошибки и статусы

Конвейер — конечный автомат по шагам: `recording → saved → transcribing → diarizing → merging → analyzing → public → done`. У каждого шага статус (`pending`, `running`, `done`, `failed`, `queued_limit`), текст ошибки и кнопка «Перезапустить шаг». Перезапуск шага сбрасывает только последующие шаги.

Типовые ошибки и что видит пользователь:

| Ошибка | Сообщение | Действие |
|---|---|---|
| Нет разрешения на системный звук | «Нет доступа к звуку приложений — пишется только микрофон» | Кнопка «Открыть настройки» |
| `mlx_whisper` не найден | «Не найден транскрибатор» | Кнопка «Установить» (`uv tool install mlx-whisper`) |
| CLI разлогинен | «Claude Code не авторизован» | Инструкция `claude /login` |
| Ответ не прошёл схему | «Скилл вернул неожиданный формат» | Показать ответ, «Повторить» |
| Лимит подписки | «В очереди: лимит подписки, повтор в 15:10» | «Повторить сейчас» |

### Заметки реализации: этап 1 (22.11.2026)

- Сборка без Xcode: SwiftPM из Command Line Tools, `make app` собирает бандл и подписывает локальным самоподписанным сертификатом «Mnemosyne Local Signing» (`make cert`). Designated requirement привязан к сертификату, поэтому разрешения TCC переживают пересборку.
- Aggregate device для tap собирается **без физического устройства**, только из tap. Если добавить в него устройство вывода, при AirPods открылся бы их микрофон и включился профиль HFP.
- Tap не отдаёт буферы, пока никто не играет звук. Дорожка собеседников начинается с первого звука, паузы внутри заполняются тишиной по host time. Смещение дорожек пишется в `othersOffsetSeconds`, склейка на этапе 3 учитывает его.
- Voice processing на macOS запускается, только если выходной узел и микшер движка созданы **до** `setVoiceProcessingEnabled(true)`, иначе ошибка −10875. Каналов на входе 9, обработанный голос лежит в канале 0.
- С VP нельзя выбрать микрофон, отличный от системного по умолчанию: VPIO либо отказывает, либо стартует без буферов. Поэтому порядок такой: VP на выбранном устройстве → VP на устройстве по умолчанию (если это оно же) → без VP. Через 2 секунды watchdog проверяет, что буферы идут.
- Запуск VP сам вызывает смену конфигурации движка. Движок перезапускается в том же графе, без пересборки, иначе получается петля перезапусков.
- Без VP выходной узел движка не трогаем: если его создать, вход и выход связываются, и микрофон MacBook при выводе в AirPods не выставляется (−10851). Формат tap на входе берём от железа (`inputFormat`), а не `outputFormat`: после смены устройства тот остаётся от AirPods (24 кГц), и `installTap` падает с ObjC-исключением.
- При смене устройства вывода tap и aggregate device пересоздаются (как и микрофон). Иначе в первой живой записи, пока звук шёл в AirPods, дорожка собеседников молчала.
- Замер эхо через динамики при громкости 44%: без VP эхо в микрофоне на 5–8 дБ выше шума, с VP уходит до уровня шума. При этом VP приглушает звук других приложений примерно на 8 дБ, несмотря на `duckingLevel: .min`.
- Дорожки во время записи: CAF, моно, 48 кГц, 16 бит (~345 МБ в час на дорожку). После Stop: AAC m4a 64 кбит/с (~29 МБ в час).

### Заметки реализации: этап 2 (22.11.2026)

- Календарь через EventKit: на этом Mac за 7 дней 29 событий, у 15 ссылка на звонок, все на Контур.Толке (`*.ktalk.ru`). Ссылки ищем в URL события, месте и описании. Распознаются Толк, Meet, Телемост, Zoom, SberJazz, МТС Линк, Teams. При нескольких ссылках приоритет у Толка.
- Режим «Авто»: офлайн при старте сами не выбираем. Если у события есть и переговорная, и ссылка, ставим гибрид, иначе онлайн. Если у события есть переговорная, нет ссылки и минуту нет звука приложений, поповер предлагает переключиться на «Офлайн». Дорожки пишутся дальше, режим влияет только на разметку спикеров.
- Название по умолчанию «Без названия». После «Остановить» сразу открывается окно названия, запись сохраняется параллельно. Если нажать «Сохранить» раньше, переименование применится сразу после сохранения.
- Событие можно сменить в поповере до записи (если сейчас идёт несколько событий), в поповере во время записи и в окне названия. Ручное название (`titleEdited`) перепривязка не трогает.
- Окно названия — `NSPanel` с `hidesOnDeactivate = false`: macOS может не дать активироваться приложению из строки меню, и без этого окно пряталось.

### Заметки реализации: этап 3 (22.11.2026)

- Конвейер: дорожки → 16 кГц моно → VAD (Silero из FluidAudio) → WAV с заглушённой тишиной → `mlx_whisper` по дорожкам по очереди. Параллельно на Neural Engine идёт диаризация (офлайн-VBx из FluidAudio 0.18.3). Затем склейка → `transcript.json` и `transcript.md`.
- mlx-whisper 0.4.3 переведён в постоянную установку: `uv tool install mlx-whisper` → `~/.local/bin/mlx_whisper`. Флаги: `--language ru --word-timestamps True --condition-on-previous-text False --hallucination-silence-threshold 2`. `HF_HUB_OFFLINE=1`: модель из кэша, в сеть не ходим.
- Скорость на M4 Pro: синтетическая встреча 9,6 мин (две дорожки, два собеседника) обработана за 53 с, это примерно 5,5 мин на час встречи. Диаризация на ней ошиблась в 1 смене спикера из 18.
- Галлюцинации режутся в три слоя:
  - тишина заглушается до распознавания;
  - слова вне отрезков VAD выбрасываются;
  - стоп-лист фраз («Продолжение следует», «Субтитры сделал…») и фильтр зацикливания («Воспоминание Воспоминание…»). Зацикливание проверяется и на склеенных репликах: Whisper размазывает его по многим односложным сегментам.
- Эхо: работает слой 3 (дедупликация по времени ±1,5 с и наибольшей общей подпоследовательности слов ≥ 0,6). Удалённые реплики сохраняются в `transcript.json` (`echoRemoved`) для проверки порога. Энергетический гейт (слой 2) пока не реализован: по замерам VP и слоя 3 достаточно. Вернёмся к нему, если на реальных встречах эхо проскочит.
- Склейка реплик: слова группируются по спикеру. Соседние реплики одного спикера сливаются, если между ними никто не говорил и пауза короче 8 с.
- Имена: «Я», «Собеседник N» по порядку появления, «В комнате N» для микрофона в гибриде и офлайне. На встрече 1:1 (один собеседник по диаризации и один другой участник в событии) подставляется имя из календаря. Эмбеддинги спикеров сохраняются в `transcript.json` для узнавания голосов (этап 7).
- Обработка идёт по UUID встречи с рабочей папкой `~/Meetings/.work/<uuid>`, поэтому переименование в окне названия во время обработки ничего не ломает. При запуске приложение дообрабатывает прерванные встречи.

## 14. Принципы интерфейса

Ориентир — лаконичные AI-заметки вроде Pocket: интерфейс не мешает читать.

- **Монохром.** Чёрный текст, серый вторичный, тонкие разделители. Красный — только кнопка записи, точка записи в строке меню и ошибки.
- **Саммари — это документ.** Колонка шириной 760 px, крупный заголовок, разделы различаются подписью и отступом, без карточек, плашек и цветных иконок.
- **Одно главное действие на экране.** В карточке это «Копировать публичное» (чёрная кнопка), в поповере — «Записать» или «Остановить» (красная). Остальные действия — текстовые ссылки.
- **Иконки только там, где без них хуже:** поиск, воспроизведение, календарь, строки онбординга.
- **Спикеры различаются именами,** не цветом. «Я» выделено насыщенностью текста.
- **Таймкоды моноширинные и серые,** клик воспроизводит аудио.
- Светлая и тёмная тема, системный шрифт SF Pro.
